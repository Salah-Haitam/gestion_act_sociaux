MarsaSocial

Plateforme de gestion des actions sociales

Application web permettant à l'administrateur RH de Marsa Maroc de gérer les prestations sociales du personnel, avec un objectif central : garantir l'équité de distribution en identifiant qui a déjà bénéficié d'un service et surtout qui ne l'a jamais reçu.

Django 5.2 + DRFReact 19 + ViteSQLite JWTscikit-learnLLM optionnel

1Vue d'ensemble

La plateforme répond à un besoin précis de la DRH : les aides sociales (aide scolaire, mariage, Hajj, naissance, décès…) sont attribuées au fil de l'eau, sans vision consolidée. Deux problèmes en découlent — des employés reçoivent deux fois le même service, et d'autres, plus discrets, ne reçoivent jamais rien. La table transaction est le cœur du système : elle relie un employé à une activité, et c'est elle qui permet de répondre aux deux questions.

Pourquoi SQLite Le volume est faible (quelques milliers de transactions pour un effectif de quelques centaines), et une base fichier rend le projet portable : le jury clone, lance deux commandes, et l'application fonctionne. Le passage à PostgreSQL ne demanderait qu'un changement dans DATABASES, l'ORM Django isolant totalement le code du moteur.

2Architecture générale

L'application suit une architecture client / serveur découplée : le front React est une application autonome qui ne communique avec Django que par des appels HTTP JSON. Cette séparation permet de faire évoluer l'interface sans toucher au métier, et rendrait possible l'ajout d'un client mobile sans réécrire une ligne de back-end.

Choix d'architecture : le proxy Vite Le front appelle /api en relatif, et Vite relaie vers Django. Conséquence : le navigateur ne fait jamais de requête cross-origin. Cela supprime d'un coup les problèmes de CORS et la résolution ambiguë de localhost sous Windows (qui pointe d'abord vers l'IPv6 ::1, où runserver n'écoute pas). En production, servir le build React derrière le même serveur web reproduit exactement cette configuration.

4Back-end Django

Le back-end est organisé par responsabilité, pas par entité : chaque fichier répond à une question unique. Un développeur qui cherche « où est la règle anti-doublon ? » trouve la réponse dans serializers.py, et nulle part ailleurs.

Rôle de chaque couche

models.py — la vérité

Définit les tables, les contraintes et les index. Deux index composites accélèrent les requêtes les plus fréquentes : (matricule, id_activitee) pour la détection de doublon, et (id_activitee, annee) pour les statistiques annuelles.

serializers.py — le contrôle

Traduit JSON ⇄ objets Python, expose les champs calculés, et surtout valide les règles métier. La méthode validate() refuse un doublon ou une année incohérente. Il refuse un doublon ou une année incohérente sur le chemin de l'API REST.

views.py — l'orchestration

Trois ModelViewSet pour le CRUD, enrichis d'actions métier (@action) : bénéficiaires, non-bénéficiaires, budget, vérification de doublon, attestations. Plus trois vues d'agrégation pour les statistiques.

filters.py — la recherche

Filtres déclaratifs django-filter : département, sexe, année, plages de montants et de dates, et deux filtres métier (a_beneficie_de, jamais_beneficie_de). Aucun filtrage en Python : tout se passe en SQL.

Principe directeur : la règle métier vit au plus près des données La validation n'est pas dans le composant React : le front affiche une alerte pour le confort de l'utilisateur, mais c'est le serveur qui garantit. L'interface prévient ; le serveur refuse.
Deux chemins d'écriture, donc deux points de contrôle Les règles sont définies une seule fois dans core/regles.py, mais appelées à deux endroits : TransactionSerializer.validate() pour l'API REST, et Transaction.clean() pour tout formulaire Django.

C'est indispensable : l'admin Django n'emprunte pas les serializers DRF. Une règle placée uniquement dans le serializer y serait silencieusement contournée — le défaut existait, un test le couvre désormais.

Performance

  • select_related et prefetch_related systématiques : la liste des transactions charge employé et activité en une seule requête, pas 1 + 2N.
  • Les totaux sont calculés par annotate(Sum(...)) côté base, jamais par des boucles Python.
  • Pagination serveur par défaut (25 lignes), ajustable par ?page_size=.
  • Le tri porte sur toute la table, pas sur la page affichée — un détail qui distingue un vrai tri d'un tri cosmétique.

6Authentification et sécurité

L'espace est réservé à l'administrateur RH. L'authentification repose sur des jetons JWT : le serveur ne conserve aucun état de session, ce qui simplifie la montée en charge et découple totalement le front du back.

1 · Connexion
identifiant + mot de passe → /auth/login/
→
2 · Jetons
accès (8 h) + rafraîchissement (7 j), stockés côté client
→
3 · Requêtes
un intercepteur Axios ajoute l'en-tête Bearer
→
4 · Expiration
sur 401, rafraîchissement automatique et rejeu
→
5 · Échec
redirection vers l'écran de connexion

Mesures en place

  • IsAuthenticated par défaut sur toutes les vues : une route nouvelle est protégée d'office.
  • Mots de passe hachés par Django (PBKDF2), jamais stockés en clair.
  • Secrets (clé d'API) dans un fichier .env exclu du dépôt ; un .env.example documente les variables attendues.
  • CORS restreint aux origines de développement — et neutralisé en pratique par le proxy Vite.
  • L'ORM paramètre toutes les requêtes : pas d'injection SQL possible.
  • React échappe le contenu par défaut : pas d'injection XSS via les données affichées.
Limites assumées — à dire au jury plutôt qu'à cacher La configuration est celle d'un environnement de développement : DEBUG = True, SECRET_KEY en clair, ALLOWED_HOSTS = ["*"], jetons conservés dans le localStorage. Une mise en production exigerait : DEBUG = False, une clé tirée de l'environnement, HTTPS, des cookies HttpOnly plutôt que le localStorage, et une liste blanche d'hôtes.

Choix de conception

Pas de bibliothèque d'état global

Redux serait surdimensionné : chaque écran possède son propre état, et la seule donnée réellement partagée — l'utilisateur connecté — tient dans un Context React.

Un composant tableau unique

Tri, colonnes personnalisables, rendu sur mesure par cellule. Utilisé par les dix écrans qui affichent des listes : un correctif profite à tous.

Tri et pagination côté serveur

Le tri est envoyé en paramètre ?ordering=. Trier sur 60 lignes en JavaScript fonctionnerait ; sur 5 000, non. Le comportement est correct dès le départ.

Graphiques accessibles

Palette validée pour les daltonismes (deutan, protan, tritan). Chaque série porte une légende et des libellés directs : l'information ne repose jamais sur la couleur seule. Idem pour les statuts budgétaires, qui portent un texte.

La bulle d'assistant L'assistant est accessible depuis n'importe quel écran via une bulle flottante. Le panneau est masqué et non démonté à la fermeture : la conversation survit à une consultation de tableau. La logique de chat est factorisée dans Discussion.jsx, utilisée à la fois par la bulle et par la page plein écran.

8Partie IA

Trois briques, toutes centrées sur l'objectif d'équité du projet.

8.1 — Score de priorisation le plus aligné avec le sujet

Pour un service donné, chaque employé reçoit une note sur 100. Plus elle est élevée, plus l'employé mérite d'être servi en priorité.

CritèrePoids (service standard)Intention
N'a jamais bénéficié de ce service40 %Le cœur du sujet
A reçu peu d'aides, toutes catégories20 %Repérer les discrets
A perçu un faible montant cumulé12 %Équité financière
Ancienneté16 %Reconnaissance du service rendu
Nombre d'enfants12 %Charge familiale

La pondération s'adapte à la nature du service : une aide scolaire ou une prime de naissance pèsent davantage le nombre d'enfants (30 %) ; un pèlerinage ou une aide au mariage pèsent l'ancienneté (25 %) et le fait de n'avoir jamais été servi (45 %). Les variables continues sont normalisées min-max sur l'effectif, afin qu'aucune ne domine par son échelle.

Chaque score est justifié Le classement affiche pour chaque ligne pourquoi l'employé est proposé (« N'a jamais bénéficié de … », « Aucune aide reçue à ce jour », « Ancienneté élevée (23 ans) »). Une recommandation opaque serait indéfendable devant un jury — et surtout devant un employé qui demanderait pourquoi il n'a pas été retenu.

8.2 — Assistant en langage naturel

Un moteur à règles, déterministe et fonctionnant hors ligne, traite la question en quatre temps.

1 · Normalisation
minuscules, accents retirés, abréviations développées (bjr, cb, jms)
→
2 · Entités
service, année, département, sexe, employé — tolérance aux fautes et aux mots collés
→
3 · Intention
dix intentions reconnues, plus politesse, employé et aide
→
4 · Exécution
requête ORM, réponse structurée : texte + tableau

Les libellés de services sont lus depuis la base : créer une nouvelle activité la rend immédiatement reconnaissable, rien n'est codé en dur. L'assistant garde le fil de la conversation — après une question sur un service, « et en 2023 ? » ou « les prioritaires ? » suffisent. Le contexte est renvoyé au client puis reposté : l'API reste sans état.

Trois garde-fous : l'assistant ne devine jamais

  1. Une question de portée globale (« qui n'a jamais rien reçu ? ») n'hérite jamais du service en cours de discussion.
  2. Une question vague (« le seul ? ») ne rejoue pas une requête au hasard : l'assistant rappelle le sujet courant et propose les suites possibles.
  3. Un critère absent du modèle (âge, salaire, situation familiale) est signalé, jamais ignoré : le résultat ne peut pas être lu comme la réponse à une question non traitée.

Renfort par modèle de langage — optionnel

Si une clé d'API est configurée, un LLM (llama-3.3-70b-versatile via Groq) complète les règles sur les tournures libres. L'architecture est délibérément restrictive :

Le LLM ne répond jamais à la question Il traduit la phrase en un plan de requête structuré (intention + entités). C'est ensuite le code Django qui exécute le SQL et met en forme le résultat.
Question
« montre-moi ceux qui méritent le Hajj »
→
LLM
plan : {intention: priorisation, service: Pèlerinage Hajj}
→
Validation
chaque valeur est confrontée à la base — l'inventé est écarté
→
ORM
le score d'équité est calculé en SQL
→
Réponse
chiffres issus de la base, jamais du modèle
  • Aucun chiffre ne peut être inventé — montants et effectifs viennent tous de l'ORM.
  • Aucune donnée nominative ne sort du serveur — seuls la question et les libellés de services et départements sont transmis. Un test le vérifie explicitement.
  • Tout est revalidé — service inexistant, année aberrante, département inconnu : écartés avant d'atteindre la couche de requêtes.
  • Les règles restent maîtresses des entités ; le LLM ne corrige l'intention que lorsqu'elles sont peu sûres.
  • Repli silencieux — clé absente, panne réseau, quota dépassé ou délai dépassé : l'assistant revient aux règles sans perte de fonctionnalité.

Mesure effectuée sur neuf formulations libres : les règles seules en traitaient huit correctement, et le LLM a corrigé la neuvième (« ceux qui méritent le Hajj » → priorisation, et non liste des bénéficiaires) sans rien dégrader. Chaque réponse indique son moteur.

8.3 — Segmentation K-Means

Le personnel est regroupé en profils similaires à partir de quatre variables standardisées : ancienneté, nombre d'enfants, nombre d'aides reçues, montant cumulé perçu. La standardisation est indispensable — sans elle, le montant (en dizaines de milliers) écraserait le nombre d'enfants. Chaque groupe est ensuite étiqueté par comparaison à la moyenne générale (« Sous-servis — à prioriser », « Bien servis »…), ce qui met en évidence les déséquilibres de distribution entre profils.

9Règles métier

Repérer les oubliés

C'est la requête qui donne son sens au projet : lister les employés qui n'ont jamais reçu un service donné. 

SELECT p.* FROM personnel p
LEFT JOIN transaction t
       ON t.matricule    = p.matricule
      AND t.id_activitee = :id_service
      [AND t.annee       = :annee]
WHERE t.id_transaction IS NULL;

Exprimée via l'ORM par Personnel.objects.exclude(matricule__in=deja_servis), elle reste lisible et protégée des injections. Le SQL équivalent figure en commentaire dans le code et dans l'interface, pour le jury.

Les trois règles d'attribution

Chaque activité porte une regle_attribution. Une seule et même fonction — core/regles.py — décide du droit ; le serializer s'en sert pour refuser une écriture, l'endpoint de vérification pour prévenir l'administrateur avant la saisie. Les deux ne peuvent donc pas diverger.

RègleConditionExemples
ANNUELLEUne fois par an et par employéAide scolaire, colonie de vacances
UNIQUEUne seule fois dans la carrièreMariage, prêt logement
ROTATIONUne fois par tourPèlerinage Hajj

La rotation équitable

Elle traduit une exigence concrète de la DRH : personne ne repart tant qu'un collègue n'est jamais parti. Un employé n'est éligible que s'il compte le minimum d'attributions observé sur l'effectif : 

attributions(employé) == min( attributions(e) pour tout e du personnel )

Cette formulation gère tous les tours sans cas particulier : au départ tout le monde est à zéro et chacun est éligible ; dès qu'un employé part, il passe au-dessus du minimum et se trouve bloqué ; quand l'effectif entier a été servi une fois, le minimum devient 1 et un deuxième tour s'ouvre pour tous.

Tour 1 ouvert
min = 0 · tout le monde éligible
→
A part
A = 1 > min = 0 · A bloqué, B et C éligibles
→
B et C partent
tous à 1 · le tour est complet
→
Tour 2 ouvert
min = 1 · A peut repartir
Deux conséquences à connaître L'arrivée d'un nouvel employé remet le minimum à zéro et referme le tour en cours : le nouvel arrivant passe avant tout second départ — c'est le comportement voulu. Et sur un effectif réel, le premier tour n'est jamais complet, si bien qu'en pratique la règle équivaut à « une fois par carrière », le second tour restant théorique. C'est assumé : la règle est juste plutôt que restrictive.

Le contrôle s'exerce à deux niveaux :

  1. Pendant la saisie — dès que l'admin choisit un employé et un service, l'interface interroge /transactions/verifier-doublon/ et affiche une alerte avec l'historique, avant tout enregistrement.
  2. À l'enregistrement — le serializer refuse la création avec un message explicite. Cette seconde barrière est celle qui compte : elle ne peut pas être contournée.

Suivi budgétaire

Chaque activité porte une enveloppe. Le consommé est la somme des montantTR ; le taux détermine un statut, accompagné d'un libellé texte et jamais signalé par la seule couleur.

TauxStatutEffet
< 80 %Sous contrôle—
≥ 80 % (réglable)Seuil atteintAlerte sur le tableau de bord
≥ 100 %DépassementReste à consommer négatif, signalé en rouge

Cohérence de l'exercice

annee est déduite de date_transaction, et une incohérence entre les deux est refusée. Sans cette règle, une saisie erronée fausserait durablement toutes les statistiques annuelles et le suivi budgétaire, sans que personne ne s'en aperçoive.

Les tests ne sortent jamais sur le réseau Les appels au LLM sont simulés (unittest.mock) et LLM_ACTIF est forcé à False en mode test. Sans cette précaution, la suite consommerait le quota de l'API et ses résultats dépendraient de la connexion — deux défauts rédhibitoires pour un test.

Vérifications complémentaires

  • Un test de rendu SSR passe les composants partagés avec des données réalistes, y compris les jeux vides et les valeurs nulles — le build et le lint ne détectent pas une exception au rendu.
  • npm run lint (oxlint) et npm run build sur le front.
  • Palette de data-visualisation validée par un outil de simulation des daltonismes.
